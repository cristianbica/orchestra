# Plan: Playbooks

Date: 2026-05-24
Workflow: investigate now; promote to `change` after approval.

## Intent

- Investigate how Orchestra should support complex reusable procedures currently discussed as abilities/skills.
- Recommend a design and implementation plan for `playbooks`: permissioned, repo-local, reusable procedures that workflows can compose.

## Evidence collected

- `.ai/docs/overview.md` confirms this repo is the Orchestra framework/template and `src/ai/**` is the distributed source.
- `.ai/RULES.md` requires controllable flow, context-aware development, token economics, tool portability, and evidence-based trust.
- `.ai/docs/features/workflows.md` defines workflows as the lifecycle/gate layer.
- `.ai/docs/features/tool-wrappers.md` says tool wrappers stay thin and point to canonical `.ai/**`.
- `.ai/docs/patterns/testing.md` says verified commands belong in memory, but memory is too small for complex procedures.
- `.ai/plans/2026-02-24-skills-support-investigation.md` is actually an overlay plan; there is no existing playbook system.
- `install.sh` copies arbitrary directories from `src/ai/**` into installed `.ai/**`, but special-cases docs/plans/memory/rules.
- `scripts/verify.sh` can be extended with structural checks for new workflow/template/playbook files.

## Findings

- Playbooks should not replace workflows. Workflows answer why/when/gates; playbooks answer how to perform a reusable operation.
- A workflow may invoke multiple playbooks during one run, such as issue fetch, anonymized data dump, and UI smoke testing inside `investigate`.
- A user may also directly ask to run one playbook through a `run-playbook` workflow.
- Playbooks may be interactive: they can ask scoped runtime questions for missing inputs, scenarios, accounts, time windows, or safety confirmation.
- Invocation policy must be explicit per playbook. Complex or sensitive playbooks cannot be auto-run just because the model thinks they fit.
- Sensitive playbooks, especially production-derived data access, need step-level approval gates even when the user has approved the outer workflow.

## Recommendation

Introduce `playbooks` as a first-class Orchestra concept below workflows and roles:

```text
Workflow = control loop, phase, approval, and output.
Role = who owns planning, implementation, or validation.
Overlay = task-specific judgment lens.
Playbook = reusable procedure with inputs, commands, side effects, approval policy, and evidence requirements.
```

Use `playbook` as the canonical term. Do not use `skill` as the canonical term because tool runtimes may already define skills differently.

## Proposed Playbook Contract

Each playbook is a concise Markdown file under `.ai/playbooks/<slug>.md` in installed repos and `src/ai/playbooks/<slug>.md` in the template source when distributed.

Required sections:

1. `Purpose` - what procedure this performs.
2. `Use when` - when agents may consider it.
3. `Do not use when` - clear exclusion cases.
4. `Invocation policy` - `auto`, `suggest-first`, or `explicit-only`.
5. `Allowed roles` - `planner`, `builder`, `validator`, `forger`.
6. `Risk profile` - side effects, data sensitivity, network/prod access, expected duration.
7. `Inputs` - required and optional runtime inputs.
8. `Runtime questions` - questions to ask only when required inputs are missing.
9. `Approval gates` - whole-playbook and step-level approvals.
10. `Steps` - ordered procedure, including setup and teardown.
11. `Commands` - exact commands when known.
12. `May call` - optional child playbooks; child invocation policies still apply.
13. `Evidence to report` - command output, files written, screenshots/traces, data provenance, cleanup status.
14. `Failure handling` - how to stop, clean up, and report partial results.
15. `Verification status` - draft/provisional/verified/deprecated and last verified date.

Invocation modes:

- `auto`: agent may run without asking inside an applicable workflow. Only for low-risk, bounded, read-only playbooks.
- `suggest-first`: agent may recommend the playbook, explain why, and wait for approval before execution.
- `explicit-only`: agent may only run when the user names the playbook or explicitly approves that exact playbook.

Sensitive approval rule:

- Playbooks that access production, production-derived data, secrets, paid services, external systems, or write non-trivial local artifacts must default to `suggest-first` or `explicit-only`.
- Per-run approval is required for production or production-derived data, even if anonymized.

## Proposed Workflow Additions

### `define-playbook`

Purpose: create or update a playbook through discovery, safety classification, command verification, and a dry run when safe.

Flow:

1. Conductor intake:
   - playbook name and goal
   - expected trigger/use cases
   - side effects and sensitive systems
   - desired invocation policy, or ask Planner to recommend one
2. Planner discovery:
   - inspect repo docs, memory, scripts, existing commands, existing playbooks
   - identify required inputs, risks, setup/teardown, and evidence
3. Planner writes a plan for the playbook definition if implementation is non-trivial.
4. Builder creates/updates `.ai/playbooks/<slug>.md` from template after plan approval.
5. Validator verifies:
   - command claims are tested or marked provisional
   - invocation policy matches risk
   - required approvals are explicit
   - docs/memory hygiene is complete

### `run-playbook`

Purpose: execute one user-selected playbook directly, with the playbook's own approval and input gates.

Flow:

1. Conductor resolves playbook by slug/name.
2. Conductor checks invocation policy:
   - `auto`: only allowed if the user request and workflow context already authorize the run
   - `suggest-first`: ask for approval
   - `explicit-only`: require explicit user naming or approval
3. Executing role asks runtime questions only for missing required inputs.
4. Executing role performs steps, respecting step-level approval gates.
5. Validator-style closeout reports evidence, side effects, files/artifacts, cleanup, and failures.

Existing workflows may invoke playbooks:

- `investigate` may compose multiple read-only or approved playbooks to gather evidence.
- `change` plans may name playbooks as verification or implementation-support steps.
- `document` may use playbooks to verify documented commands.
- `guided` may wrap either `define-playbook` or `run-playbook` for step-by-step control.

1. Add `src/ai/workflows/define-playbook.md`.
2. Add `src/ai/workflows/run-playbook.md`.
3. State that playbooks do not bypass workflow gates or role boundaries.
4. State that child playbooks inherit and enforce their own invocation policy.
5. Add approval rules for sensitive data, external systems, long-running tasks, and local artifact writes.

### Phase 3: Wire Conductor/Planner/Builder/Validator behavior

1. Update `src/ai/agents/conductor.md`:
   - route playbook definition to `define-playbook`
   - route direct execution to `run-playbook`

   - allow existing workflows to recommend or invoke playbooks according to policy
2. Update `src/ai/agents/planner.md`:
   - discover relevant playbooks during planning
   - include playbook invocation and approval requirements in plans
3. Update `src/ai/agents/builder.md`:
   - execute approved playbooks only inside approved scope
   - report evidence and side effects
4. Update `src/ai/agents/validator.md`:
   - validate playbook policy/risk alignment
   - validate playbook execution evidence
   - reject undocumented command claims unless marked provisional
5. Update `src/ai/agents/guides/delegation.md` and context-management guidance only where needed.

### Phase 4: Update workflow docs and human docs

## Open Decisions

1. Should the canonical folder be `.ai/playbooks/` or `.ai/tasks/`? Recommendation: `.ai/playbooks/`.
2. Should `run-playbook` be a primary workflow or a workflow wrapper? Recommendation: primary workflow, because it has unique approval and input gates.
3. Should `define-playbook` require plan approval before writing? Recommendation: yes, unless the edit is trivial wording in an existing playbook.
4. Should a non-sensitive `auto` playbook be executable during planning? Recommendation: only if read-only, bounded, non-mutating, and the role/workflow allow it. Planner remains read-only.
5. Should plan approval count as playbook execution approval? Recommendation: only when the plan names the exact playbook, inputs, side effects, and approval scope. Production-derived data still requires per-run confirmation.

## Non-goals

- Building a runtime engine or parser for playbooks.
- Generating tool-native skills for Claude, Codex, or other adapters in this pass.
- Adding company-specific or Rails-specific playbooks to the generic Orchestra template.
- Weakening the existing plan approval gate.
- Moving command reference material out of `.ai/MEMORY.md`; memory should keep short verified commands, while playbooks hold complex procedures.
